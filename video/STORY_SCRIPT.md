# Merge Queue — two-minute story

## Story shape

**Specific person → urgent job → collision → visible consequence → product intervention → measurable proof → human control → larger implication**

The protagonist is Maya, a launch lead who cannot stop working while an agent reorganizes her project board. The central proof is not a feature list. It is the compression of twenty-six proposed field outcomes into three human decisions with zero lost work.

## Timed script

### 0:00–0:07 — Open with the result

**On screen**

> 26 CHANGES · 3 DECISIONS · 0 LOST WORK

**Voiceover**

> An agent changed twenty-six fields while I continued working. I reviewed only three—and none of my work was lost.

### 0:07–0:20 — One person, one deadline

**On screen**

> THURSDAY · 4:42 PM
>
> MAYA HAS A FRIDAY LAUNCH.

**Voiceover**

> It’s Thursday afternoon. Maya is preparing a product launch for Friday. She asks an agent to reorganize the launch board—but she cannot stop working while it runs.

### 0:20–0:34 — The collision

**On screen**

> AGENT: BASE R1
>
> HUMAN: MAIN R5

**Voiceover**

> The agent branches from revision one. Meanwhile, Maya changes owners, deadlines, and workflow status. By the time the agent finishes, the board is already at revision five.

### 0:34–0:45 — The hidden danger

**On screen**

> MEMORY ≠ CONCURRENCY CONTROL
>
> MAYA CHOSE MAYA · AGENT PROPOSED DEV

**Voiceover**

> The agent remembers every tool call. But that history cannot decide whether Maya or Dev should own security. If the agent writes directly, someone’s decision disappears.

### 0:45–0:55 — The intervention

**On screen**

> MERGE QUEUE
>
> GIT-STYLE CONFLICT RESOLUTION FOR LIVE APPS

**Voiceover**

> That’s why we built Merge Queue: Git-style conflict resolution for humans and agents editing the same live application.

### 0:55–1:35 — The live proof

**On screen**

> 22 SAFE · 1 SAME · 3 YOUR CALLS

**Voiceover**

> Through WebMCP, the agent reads the board, opens an isolated branch, and stages thirteen operations. Merge Queue compares its base, Maya’s current board, and the agent proposal. Twenty-two changes are safe. One matches. Only three need human judgment. Maya keeps Friday, chooses herself as owner, and leaves the demo in progress. Everything else merges automatically.

**Visual sequence**

1. Three live WebMCP receipts appear.
2. The branch opens from revision one and holds thirteen staged operations.
3. Four human edits advance main from revision one to revision five.
4. The three-way merge reveals twenty-two safe changes, one same result, and three conflicts.
5. Maya resolves deadline, owner, and workflow.
6. The combined result lands as revision six.

### 1:35–1:45 — Human control

**On screen**

> HUMAN-ONLY COMMIT · REVERSIBLE BY DESIGN

**Voiceover**

> The agent cannot resolve these conflicts or commit the merge. Maya approves one atomic revision—and can revert it without erasing history.

### 1:45–1:54 — Why WebMCP

**On screen**

> STRUCTURED TOOLS · VERSIONED STATE
>
> VISIBLE OPERATIONS · NARROW PERMISSIONS

**Voiceover**

> WebMCP makes this possible inside the live application: structured tools, versioned state, visible operations, and narrow permissions.

### 1:54–2:00 — The belief

**On screen**

> AGENT SPEED. HUMAN JUDGMENT.

**Voiceover**

> Agents bring speed. People keep judgment. Merge Queue makes room for both.

## Direction

- Begin with the measurable result, not the team or the technology.
- Keep Maya as the story’s subject throughout.
- Treat the three-way merge as the climax and hold the 22 / 1 / 3 result long enough to read.
- Show real product screenshots whenever the interface is on screen.
- Use silence between narration blocks as deliberate viewing time.
- End on the collaboration principle, not a feature list.
